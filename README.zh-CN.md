# 许愿式编程与局部开发范式

[English](README.md) | 简体中文

## 1. 背景: 一年前和现在

- 一年前 agent 只能处理短任务, 编码主要在 VS Code, Cursor 这类 IDE 里进行, 用户把文件拖进对话, 选中具体的代码行, 给 agent 提供精确的上下文
- 那时 agent 的角色是 copilot, 人和 agent 结对编程: 人给出局部的功能描述, 让 agent 写一段, 自己 review, 运行和测试, 再把问题反馈给 agent
- 这种方式推进顺畅, 产出的代码质量高
- 现在 agent 能处理持续 2 小时到几天的长任务, 可以调用 subagent, 跨多个会话运行, 使用 goal 类工具
- 用户的预期随之提高, 希望效率提升 2 倍到 100 倍

## 2. 许愿式演示的问题

- 自媒体用最新模型做 "许愿式" 的演示: 写一句需求, 等 agent 交付完整作品, 公司也把这类演示当作能力亮点来宣传
- 演示效果惊艳, 但属于一次性作品: 没有人知道它内部怎么运行, 后续无法修改, 维护和迭代
- 模型公司的条件跟普通团队不同: 内部 token 几乎不受限制, 可以让多个 agent 同时开发, 测试和验证, 而且做的多是从零开始的新功能, 没有历史代码的包袱
- agent 数量足够时, 许愿式编程也能做到良好的工程质量, 从零搭建边界情况测试, 单元测试, 集成测试和端到端测试, 问题在于实现细节没有人清楚
- 对维护 10 年以上复杂软件的传统公司, 这种方式难以落地:
  - 改动一个功能, 会让其他功能出错
  - 没有文档, 没有回归测试, 没有单元测试
  - agent 无法判断新写的代码是否正确, 也无法判断旧功能有没有被改坏
- 开发新功能和维护遗留系统这两种场景, 许愿式编程的适用程度差别很大

## 3. 核心做法: 由 agent 执行的局部开发与验证循环

- 继续使用最新的模型和 agent
- 开发流程沿用一年前的局部循环: 任务拆小, 写一段, 测一段, 验证一段, 每个阶段通过验证才进入下一个阶段
- 区别在于由 agent 从头到尾执行, 以前人做的 review, 测试和反馈也交给 agent, 这些工作怎样交接给 agent, 是这套方法要解决的核心问题
- 以前结对的人和 agent 是两个不同的思考主体, 现在负责开发的 agent 需要一个搭档 agent 模拟人的角色: review, 测试, 验证, 并控制整体节奏

## 4. 愿望的验证

- 负责许愿的 agent 也会许错愿, 愿望要经过验证, 不能默认它是对的
- 验证分两层:
  - 第一层, 愿望要能被机器检查: "加一个登录按钮" 这类模糊的愿望写不成可执行的验收标准, 许愿的 agent 要反复改写, 直到愿望可以验证
  - 第二层, 愿望对不对只能由人判断: 每批愿望提交之前, 人先过一遍, 确认方向没有跑偏
- 每个愿望都要有验收标准, 执行结果按这个标准检查
- 人的工作从逐行 review 代码变成 review 愿望: 检查任务拆分对不对, 验收标准够不够严, 愿望是自然语言, 一批几分钟就能读完

## 5. 愿望是逐步浮现的

- 愿望一开始是模糊的, 先跟 bot 对话, 定下整体方向和具体的愿望
- 定下来之后, 只有最初几步是明确的, 后面只有一个大概的方向, 或者只是一种感觉
- 前面的愿望不断实现和测试, 我对系统有了新的认识, 后面的愿望就越来越清晰, 有时新的认识会推翻之前的感觉, 结果跟直觉相反
- 所以不能一开始就把所有愿望编排好, 愿望是在推进过程中逐渐清晰的
- 这是这套方法跟目前主流的许愿式编程, 以及一些开源工作流的主要区别: 它们在开始时就把整个愿望拆分和编排好, 这里只编排已经明确的部分

## 6. 编排与推进

- 编排分两部分:
  - 已经明确的前几步, 拆成子愿望, 按依赖关系分成串行和并行
  - 后面模糊的部分, 只记下方向, 每完成一批愿望, 再根据新的认识补充, 调整或推翻
- 推进时跟踪当前状态:
  - 先执行哪一步, 当前这一步的状态
  - 这一步完成后接着执行哪些步骤, 能不能并行
  - 这些串行或并行任务各自的状态

## 7. 探索与验证的循环

- 明确的几步完成后, 接下来的步骤以想法的形式出现, 有的是确定的, 有的还不确定
- 确定的想法, 我直接告诉 agent 去做
- 不确定的想法, 交给 agent 继续搜索和探索, 并实际运行验证, 再汇报验证了哪些想法, 实际效果是什么
- 我和 agent 一起把验证过的模糊想法变成具体的, 确定下来的愿望, 继续往前推进
- 这个过程反复进行, 一些想法一步一步从模糊变得具体
- 每一轮记录两样东西:
  - 已经实现了什么
  - 探索和验证的过程本身: 试了哪些想法, 实际效果是什么
- 远期目标始终作为参照: 往上探索和验证的东西越多, 浮现出来的具体的新东西也越多, 一步步接近远期目标

## 8. 一步一测与集成

- 改掉以前的习惯: 先把代码全部写完, 最后统一测试, 这样很多情况测不到, 问题集中暴露, 代码已经写完再修, 改起来难度大
- 实现一步, 测试一步, 验收一步, 这一步没问题再进入下一步
- A 和 B 互相独立, 最后一步把 A 和 B 集成起来:
  - 单独写 A 时, 按 A 自己的标准做, 暂时不考虑集成
  - 集成时发现 A 和 B 各自的设计有问题, 再回去修改 A 的实现和它的验收标准, 这种修改不算破坏 A 原来的验证标准

## 9. 维护没有文档, 没有测试的老项目

- 适用的项目: 维护多年, 代码量大, 没有文档, 没有单元测试和集成测试, 不好测试
- 先统一测试名词: 测试的名词多, 每个人理解不一样, 所以先说清楚这几种测试各自负责什么, 覆盖什么:
  - 单元测试: 测一个函数, 类或模块自己的逻辑, 外部依赖用 mock 或 stub 替换, 覆盖分支, 边界值和异常输入, 运行快
  - 集成测试: 测几个模块之间, 或模块和数据库, 外部接口等依赖连起来之后的配合, 覆盖接口约定, 数据格式和调用顺序
  - 端到端测试: 从用户入口 (界面或对外接口) 出发, 按真实业务流程走完整条链路, 覆盖业务流程能不能走通, 用例少, 运行慢
  - 回归测试: 每次改动之后重跑已有的用例, 确认原来正常的行为没有被改坏, 用例可以来自单元测试, 集成测试和端到端测试, 也包括行为基线和修 bug 时补的用例
  - 单元测试, 集成测试, 端到端测试按测试范围区分, 回归测试按用途区分, 两种分法可以重叠
- 以后开发新功能时, 要写明哪些部分需要单元测试, 哪些需要集成测试, 哪些需要回归测试, 哪些需要端到端测试
- 先建立行为基线:
  - 让 agent 把系统跑起来, 抓取接口, 记录输入和输出, 给没有文档的系统补一层黑盒测试
  - 之后每次改动都用这份基线做回归验证, 不依赖人工 review
  - 基线建好之后, 不断给它补相关的文档和测试
- 用测试当文档, 这是一个待验证的想法, 我还不确定这种方式是否可行:
  - 文档总会过时, 我现在的做法是文档只做快速索引: 几个文件, 介绍项目是做什么的, 有哪些业务, 大概的业务流程在哪些组件或模块里, 模块里关键的几个文件或类型是什么, 这类索引不容易变
  - 其他关键设计放在注释里, 通过快速索引找到关键文件或类型, 再看注释和源码, 就能把项目梳理清楚
  - 边缘 case 也是一种文档, 但很多 case 由测试团队自己保存, 没有文档化, agent 也难以获取
  - 复杂的老项目里, 有些模块不知道被哪些业务流程用到, 这类模块适合用测试做边界保护: 一个模块在历史开发中被 A, B, C 等多个流程分别涉及, 对应的端到端测试或回归测试一定要有
  - 以后改动这个模块时, 读测试就能知道它在哪些业务流程里, 每个测试走一遍业务流程, 能大致涵盖已有的业务流程
  - 所以有的地方用单元测试, 有的地方用集成测试或回归测试, 覆盖各种 case 的回归测试可以作为文档的一种

## 10. 记录: commit 和注释

- 验收标准的变更记在 commit 里, 文档里的注释不用来记这件事:
  - 每次修改验收标准, 都在 commit message 里写明原因, 例如: "集成时发现 A 和 B 的接口约定冲突, 标准从 X 改为 Y"
  - 不记录的话, 以后翻 git 历史只能看到测试改了, 看不出是 A 写错了, 还是标准本身有问题, 记下来之后, 看代码的人可以追溯完整的决策过程
- 注释只写在函数声明和关键逻辑处, 写两类内容:
  - 关键设计: 这段代码是怎么设计的
  - 代码之外的信息: 整体功能的外部依赖, 理解这段逻辑背景需要的参考文档或文献, 修 bug 时对应的 issue 文档, 以及其他只能通过注释说明的内容
- 有些代码当时写得不好, 出于某些原因做了特定的 workaround, 这类做法尽量不写进注释, 因为 agent 以后可能学会这些坏习惯, 注释里只留好的做法
